# UMG probe: script a widget through Epic's MCP server, capture it offscreen, set up Common UI

Run the launcher commands below from the plugin root. They wrap each complete probe in the [shared owned process tree](../engine_lock/README.md); retained scientific results describe their original runs.

Probes eight questions about UMG and Common UI on Unreal Engine 5.8, Windows: which UMG, MVVM and widget-animation toolsets Epic's MCP server lists, whether a script can build, compile and save a Widget Blueprint through them, whether that widget can be captured in a Play-In-Editor session run offscreen, whether the Common UI quickstart's requirements can be set from a script and an activatable widget activated, whether the Sequencer and Control Rig tools can add a track and a key to a widget animation, whether the MVVM toolset can create a view model, add it to a widget and bind it to a text block, whether the running game viewport client is the Common one, and whether a simulated key or click changes the active Common button. Nothing here needs a project of yours: the runner makes throwaway projects in the OS temp folder.

Status: Ran 2026-10-30 from a session with no desktop (SSH, one engine process at a time). The first four groups scored 23 of 24 (`toolsets` 5 of 6, `widget` 4 of 4, `capture` 6 of 6, `commonui` 8 of 8; the failing check was that no widget-animation toolset is listed). The four added groups ran in three engine runs each: `animation` 1 of 4: the eight `animation_toolset.*` toolsets (Sequencer, keyframing, Control Rig and five more, 319 tools) are described and their descriptions kept, and no tool can add a track and a key to a widget animation; editor Python makes the `WidgetAnimation` and `MovieScene` objects but cannot link them (the properties are protected), the level-sequence tools refuse a widget animation by type, and `add_track_to_binding` fails for want of a binding, so nothing saved reads back. `mvvm` 4 of 6 in the scripted run and the full chain by hand in the same run: `CreateViewModel`, `AddViewModelProperty` (pin type "text", a default value is required), a compile of the view model blueprint (without it `CreateViewBinding` says "Property does not exist"), `AddViewModelToWidget` (the generated `_C` class), `CreateViewBinding` (`conversionName` "" is required), the three `List` tools, a compile and a save, and a fresh editor lists the view model and the binding. `viewport` 3 of 3: the running game viewport client of the offscreen Play-In-Editor session is `CommonGameViewportClient`, the saved class, read by the stage script and listed by the engine. `input` 4 of 5: the Slate inspector toolset (14 tools, `Click`, `Hover`, `PressKey` and `Snapshot` among them) delivers a click to the editor's Content Drawer button and its snapshot lists the active Common button, and a direct call of the button's delegate logs a line; no route changed the Common button (the Slate `Click`, `Hover` and `PressKey` returned true and left the click counter and every button state read back unchanged; Python has no `input_key` on the player controller and no click function on the button). The Slate click is aimed at the middle of a UMG widget's reported size, which is about twice its size in the frame at this viewport scale, so a miss by aim is possible and was not separated from a dropped event. Not shown: input on a physical device, button styles, a widget animation written by a C++ bridge.

## Run

```text
pwsh -NoProfile -File examples/unreal/engine_lock/with-engine-lock.ps1 node examples/unreal/umg/umg_probe.mjs --engine "C:/Program Files/Epic Games/UE_5.8" [--only toolsets,widget,capture,commonui,animation,mvvm,viewport,input] [--keep] [--plan] [--hold] [--port <number>]
```

`--plan` prints what would run. `--hold` keeps the editor of the session phase (or of the play phase) open after its scripted steps and answers request files until `end.flag` appears: a toolset call, a toolset description, a Python snippet or a read of the stage report per file (`umg-hold.mjs`), each run once; it is for exploring a session by hand and the scripted probe does not need it. `--keep` leaves the project folders (a run with a failing check keeps them anyway; they hold `Saved/*.json` reports, the MCP traces of the session phases, `Saved/Logs` and `Saved/Screenshots`). The exit code is 0 when every check of the groups that ran passes, 1 when a check fails and 2 on a usage error. A clean run deletes the projects.

| Group | Question | Phases |
|---|---|---|
| `toolsets` | Over loopback, do `list_toolsets` and `describe_toolset` list the UMG, MVVM and widget-animation toolsets with their tools? | session |
| `widget` | Can a Widget Blueprint with a canvas, a text block, a button and an image be created, given properties, compiled and saved through those toolsets, and does it read back? | session (with `toolsets`) |
| `capture` | Is that widget visible in a frame saved from a Play-In-Editor session run offscreen, and by which capture route? | capture (a new editor loads the saved widget) |
| `commonui` | Can the Common UI quickstart's pieces (the Game Viewport Client Class, Common Input Settings, an input action data table) be set from a script, and does an activatable widget with a Common button read back active and show in a frame? | session, capture (a second project with the Common UI plugin) |

| `animation` | With the eight Sequencer and Control Rig toolsets described, can a track and a key on a widget property be added to a widget animation of a saved Widget Blueprint through them and read back by a fresh editor? | session (with editor Python beside the server), readback |
| `mvvm` | Can the MVVM toolset create a view model with a property, add it to a Widget Blueprint with a text block and bind it to the block, do the three `List` tools read it back, does the blueprint compile and does a fresh editor load it with the binding? | session, readback |
| `viewport` | In an offscreen Play-In-Editor session of the Common UI project, is the running game viewport client the `CommonGameViewportClient` that the settings saved? | session, play (a second project with the Common UI plugin) |
| `input` | Does a simulated key or click delivered to the active Common button change a log line, a state read back or a frame, by any route (Python, the Slate inspector toolset)? | session, play |

`toolsets` and `widget` share one editor session; `capture` runs after it and needs the widget the session saved, so naming `capture` runs the session first. `animation` and `mvvm` share that session too (each builds its own small Widget Blueprint with a canvas and a text block) and are followed by the readback: a fresh editor that reads the saved blueprints back. `viewport` and `input` share the play phase, which follows the Common UI session. The Common UI pieces live in their own project so that the first project's frames are not taken under another game viewport client.

## How a run works

- **Session phase.** A rendering editor starts with `-RenderOffScreen -unattended` (no window, no interactive session) and the MCP server started by launch flag on a free port (`-ModelContextProtocolStartServer -ModelContextProtocolPort=<port>`). The runner polls until the server answers, then drives it over loopback with the session handshake: an `initialize` POST (`Accept: application/json, text/event-stream`, the `Mcp-Session-Id` response header kept), the `notifications/initialized` notification, then `tools/call` of `list_toolsets`, `describe_toolset` (argument `toolset_name`) and `call_tool` (arguments `toolset_name`, `tool_name`, `arguments`). The server runs calls serially on the game thread, so calls never overlap and a write is never sent twice: only a call refused because the tool name was not found is sent again, with the other spelling of the name.
- **The tools are found, not assumed.** `list_toolsets` is read for the toolset names (the UMG toolset, an MVVM toolset, a widget-animation toolset, and the object, asset, Blueprint, data table and settings toolsets the other steps use), `describe_toolset` for the tool names and argument names. Argument names are matched against the described schemas. Property values are never written blind: each property is read with `get_properties`, and a struct is written back in the spelling that was read (only the changed fields, then the whole value if that is refused).
- **Stage phase.** A second editor runs `umg_stage.py` with `-ExecCmds="py ..."`: a blank saved map, Play In Editor, a frame with no widget, the widget created and added to the viewport, the same frame again, each by two routes (the console command `Shot showui`, and `AutomationLibrary.take_high_res_screenshot`). The runner reads the PNGs and judges regions of them.
- **Editor Python beside the server.** The session phase also starts the stage script in its `rpc` mode (`UMG_RPC` names a folder): it runs `request.py` there once on the game thread and writes `result.json`. `umg_anim_container.py` is such a snippet: it makes the `WidgetAnimation` and `MovieScene` objects and tries every link. The editor starts with the MCP server and the Python in one process.
- **Play phase.** One editor with the MCP server and the stage script in its `input` mode: it plays, records the running viewport client (and runs `obj list class=GameViewportClient`, whose lines the runner copies from the log), makes the Common button active, binds its `OnButtonBaseClicked` delegate to a counter and waits at a barrier file. Meanwhile node calls the Slate inspector toolset over loopback (it describes it, observes all windows, takes a snapshot, finds the ref of the widget named GO, hovers, clicks and presses Enter, and clicks the editor's Content Drawer button as a control), reading the counter and the button state the stage script rewrites once a second; then it writes the barrier file and the stage script tries its own routes (a control that calls the delegate, focus, `input_key`, a button function, `on_key_down`) and saves a frame before and after.
- **Judging.** The checks are pure functions of the reports (`umg-probe-checks.mjs`); the widget's anchors are fractions of the viewport, so the regions do not depend on the DPI scale. A window frame holds the editor around the viewport, so a solid blob of the button colour that appeared between the two frames places the viewport, and the text region is judged inside it against a control region beside it.
- Video memory is sampled with `nvidia-smi` (when it is on the PATH) before and after each editor phase; a log that reports a video-memory failure is printed as `not run: memory`.

## Files

| File | What it does |
|---|---|
| `umg_probe.mjs` | the runner: options, one throwaway project per group set, the editor phases, the frames read back, the judging |
| `umg-probe-checks.mjs` | the options, the phase plan, the MCP response and property-shape helpers, the frame judging and one check per claim |
| `umg-mcp.mjs` | the MCP client over loopback (handshake, `tools/list`, `tools/call`, event-stream and JSON responses, timeouts) |
| `umg-session.mjs` | the session steps: discovery, the widget build and read-back, the Common UI pieces |
| `umg_stage.py` | the Play-In-Editor half: plays a blank map, creates the widget, activates it (Common UI), takes the frames, quits; also the rpc mode, the viewport client read and the input routes |
| `umg-hold.mjs` | calling into an open editor: `pyCall` (Python through the stage script), `answerRequest` and `holdLoop` (`--hold`) |
| `umg_anim_container.py` | the editor Python of the animation group: makes a widget animation and its movie scene and tries to link them |
| `umg-probe.test.mjs` | canned reports with a failing case per check, generated frames, and the client and the session run against a fake MCP server |

## What the runs showed

- **MCP server.** Started by launch flag in a rendering editor with `-RenderOffScreen -unattended`; it answered about 16 s later with no click. `initialize` returned protocol 2025-11-25 and a session id; `tools/list` names the three meta tools; `list_toolsets` answers with text (one `- <module>.<class>: <description>` line per toolset), `describe_toolset` with JSON (the toolset and its tools, each with an input schema, camel-case argument names for C++ tools, snake-case for Python ones); `call_tool` takes the tool name without its toolset prefix and an `arguments` object, and returns `{"returnValue": ...}` as text.
- **Properties.** The UMG toolset returns widget and slot references; the object toolset reads and writes their properties as JSON (`values` is a JSON string). Colours and structs read back as JSON strings with lower-case keys; a struct is written back with only the changed fields.
- **Creating a widget in Play In Editor.** Python has no `WidgetLibrary.create`; `unreal.new_object(widget_class, player_controller)` followed by `add_to_viewport` made an instance that drew.
- **Frames.** The console command `Shot showui` saves the editor window (the widget is inside the Play-In-Editor viewport, smaller than the frame); `AutomationLibrary.take_high_res_screenshot` saves the scene only.
- **Common UI settings.** The settings toolset (`ConfigSettingsToolset`) finds Game Viewport Client Class in Project / Engine / General and Input Data in Project / Game / CommonInputSettings, sets and saves them; the viewport class is read at the next editor start.
