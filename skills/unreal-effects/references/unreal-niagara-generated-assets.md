# Niagara: generated assets, a flipbook, a mesh and a frame parameter

Written for Unreal 5.8. A [tested] line ran in [`nts_probe.mjs`](../../../examples/unreal/niagara_toolsets/README.md) (`--only wire` passed 10 of 11 checks, `--only frame` 5 of 5) on a throwaway project: it shows one project and one scene, not a general rule. A [documented] line names Epic's documentation or a file under the engine's `Engine` folder. Call shapes are in [Author Niagara systems from Python](unreal-niagara-toolsets.md); the rest of the Niagara routes are in [Niagara](unreal-niagara.md).

## Sprite atlas to a flipbook

- [documented] Import the atlas, use a Sprite Renderer with the Sub UV Animation module, and set Sub Image Size to the atlas grid. Epic advises a power-of-two texture and a tile count that divides it evenly. The Niagara Baker, which bakes a simulation to a flipbook, is an editor UI workflow.
- [tested] 2026-10-29: an agent-sprites atlas (128 by 64 pixels, 4 by 2 cells of 32 pixels; its JSON lists 16 rectangles, the 8 cells and a copy for the animation tag) imported as a texture. The grid came from the most common cell size, `SetRendererData` stored `SubImageSize` `{"x":4,"y":2}` on the sprite renderer with the SubUV material, and the system emitted 3 particles.
- [tested] 2026-10-29: `Particles.SubImageIndex` read 1.95 after 10 frames and 5.98 after 60 (the atlas has 8 cells), and the screenshot changed 33,543 of 921,600 pixels against a baseline with the actor hidden. A generated 8 by 10 atlas passed the same chain earlier.

## Direct Frame Index and a user parameter

- [tested] 2026-10-29: the build worked every time: `AddUserVariables` added and `GetUserVariables` listed `User.FrameIndex` (float); SubUV Animation Mode was set to Direct Index; `SetStackInputData` linked Direct Frame Index, read back as `NiagaraExt_StackInputData_Linked` naming `User.FrameIndex`; a new process re-reading the saved asset showed both, and `GetSystemCompileState` read `UpToDate`.
- [tested] 2026-10-29: loaded as saved, the frame did not follow the link: `Particles.SubImageIndex` was exactly 16 times `Particles.NormalizedAge` with the parameter set to 0, 2 and 9, and the screenshots at 2 and 9 were identical (5,102 changed pixels each). With `fx.ForceCompileOnLoad=1` in the project's `[ConsoleVariables]`, which the editor process reads at start, it read 0, 2 and 9, the three screenshots differed, and all 5 `frame` checks passed ([the recipe](unreal-niagara.md)).
- [documented] The toolset edits with auto compile off, requests no compile after a link, and Python cannot request one (`UNiagaraSystem::RequestCompile` is not exposed): recompile on load before relying on a link. A stale compile as the cause is inferred from the source and from the recompile changing the result.
- [general] On an earlier engine build a constant 5.0 written into Direct Frame Index took effect with no link, and four variants left the frame age-driven (the short parameter name, a default of 5.0, the mode written again after the link, a link to `Emitter.Age`); none was repeated with the recompile.

## Mesh renderer

- [documented] A mesh renderer takes its mesh from a slot (`Meshes[i].Mesh`), from a slot binding to a Static Mesh object parameter (`Meshes[i].MeshParameterBinding`), or through `MeshesBinding` from a data interface that implements the renderable-mesh-array interface; the slot's `Mesh` is the fallback when a binding resolves to nothing (`NiagaraMeshRendererProperties.cpp`, `NiagaraMeshRendererMeshProperties.h`). `override_system_user_variable_static_mesh` looks up a parameter of the data-interface type, so it is not a route to the renderer's mesh.
- [tested] 2026-10-29: a rigged vulpine GLB (19 joints, 48 mesh nodes) imported with the combine-by-skeleton pipeline gave 1 skeletal mesh and no static mesh. A static export of the same model (the same geometry with the bones, skin and clips removed, one mesh) gave 1 static mesh; `SetRendererData` stored it, the system emitted 87 to 160 particles and the screenshot changed 54,879 of 921,600 pixels. A rigged model reaches a mesh renderer through a static export, not through the skeletal import.
- [tested] The built-in cube imported as one static mesh (`.../StaticMeshes/cube.cube`, 2 assets) and the same chain passed with it.
- [tested] `GetRendererData` of a mesh renderer lists nested struct fields in lower camel case (`mesh`, `lODBias`, `lODMode`). A mesh written under the key `Mesh` returned no error and the read-back still had no mesh; written under `mesh` the read-back held the same asset path ([renderers](unreal-niagara-toolset-renderers.md)).
- [tested] A mesh emitter added to a template-made system started dead and emitted after a write of the system's `Loop Duration`: see [Emitters added to a template-made system start dead](unreal-niagara-toolsets.md).

## Static Mesh user parameter

- [tested] `AddUserVariables` with the data-interface type `/Script/Niagara.NiagaraDataInterfaceStaticMesh` returned no error and no value and `GetUserVariables` listed nothing, with a default carrying only `dataInterfaceClass` and with one that also named an instance made in Python. Type `/Script/Engine.StaticMesh` with a `NiagaraExt_VariableValue_Object` default (`objectClass`, `object`) added the parameter and listed it.
- [documented] `AddUserVariable` returns without a message when the default is invalid, and builds the default from `DataInterface` (the instance), not from the class (`NiagaraExternalSystemEditorUtilities.cpp`, `FNiagaraExt_VariableValue::Get`).
- [tested] 2026-10-29, the binding JSON: `GetRendererData` lists on each mesh slot `meshParameterBinding` as `{"aliasedParameter": {"name": "None", "typeDefHandle": {"registeredTypeIndex": 105}}, "resolvedParameter": {...the same...}}`. `SetRendererData` with the slot written back (the whole `Meshes` array, the slot's `mesh` kept) and `User.MeshBind` in both names returned no error for every index tried (111 to 132) and read the same JSON back, so it does not say whether the index is right. The index is a session registry number with no readable name.
- [tested] 2026-10-29: of those 22 copies, indices 117 and 118 drew the parameter's default mesh (a sphere) instead of the slot's cube, about 71,000 pixels from the unbound control; the other 20 drew the cube. 121, the index the registration order in `NiagaraModule.cpp` suggests for the Static Mesh type, did not. Which of 117 and 118 is the Static Mesh type was not found.
- [tested] 2026-10-29: on those two copies `set_variable_static_mesh` (a cone) ran with no error, and the next shot drew the slot's cube, within about 550 pixels of the control's. The call did not swap the drawn mesh in this scene, and the cause was not found in three runs. The mesh route that works is `SetRendererData` with `Meshes[0].mesh`.
- [tested] `override_system_user_variable_static_mesh` on the copy with the unbound object parameter ran without an error and the system still emitted (80 particles): a clean return does not show that a mesh was bound.
- [general] Smallest next experiment: bind a slot to a Static Mesh parameter in the editor UI, read its `meshParameterBinding` back for the real index, and test `set_variable_static_mesh` there.
