# Chaos destruction from C++: hulls, simulation data and spawn order

Written for Unreal 5.8. A [tested] line ran in [`chaos_break.mjs`](../../../examples/unreal/chaos_break/README.md) with 11 of 11 checks (headless, and with `--material project --render`) and the break-event counts the lines below name; the other numbers are in the example's README. A [documented] line cites a file and line in the install as `Module/File`, found by name under `Engine/Source/Runtime` or `Engine/Plugins`. A [general] line is behaviour observed outside this repository and not re-run here. Building a collection and the material flag are in [Chaos destruction from C++](unreal-chaos-destruction-native.md); editor routes are in [Chaos destruction](unreal-chaos-destruction.md).

## No convex hulls, nothing breaks

- [documented] `FGeometryCollectionConvexUtility::GetValidConvexHullData(FGeometryCollection*)` (`Chaos/GeometryCollectionConvexUtility.h` line 104, body in the `.cpp` lines 146-181) creates the hull attributes if missing and adds a hull for every rigid transform with none.
- [documented] `AppendStaticMesh` copies only the mesh's simple collision into `ExternalCollisions` (conversion `.cpp` lines 120-162, 350), which the proxy uses only if `bUseImportedCollisionImplicits` is set (`GeometryCollectionPhysicsProxy.cpp` line 5736). Neither it nor `FractureEngineFracturing.cpp` builds hull data. The default collision shape is convex (`GeometryCollectionObject.cpp` line 186), and a convex shape is made only from hull data (proxy lines 5239-5253).
- [documented] A transform with neither a shape nor a cluster built from its children logs `GeometryCollection Transform %d has no geometry` (proxy line 3217), then `Geometry collection %ls tried to create %d particles with no geometry` (line 3227; line 3231 omits the name). Both are `Verbose`. The engine's comment at line 3216 names another cause: "This will happen if some particles are being culled (e.g., via data flow) but the MaxSimulatedLevel is set to a level that includes them."
- [tested] In a running game, a collection built from code with hulls (24 of 25 transforms with a hull, a 0.25 MB file) gives 24 break events (24 distinct pieces) from strain alone. The no-strain control gives 0 when spawned high enough not to reach the floor. In the first run the control, spawned at 5000 cm, reached the floor and broke 24 pieces from impact; the probe now spawns it at 100000 cm.
- [tested] A collection with no hulls gives 0 break events and the log line `tried to create 24 particles with no geometry` naming the actor. A component without a physics proxy also gives 0. The no-geometry lines appear only with `-LogCmds="LogChaos Verbose"` (or `-ExecCmds="log LogChaos Verbose"`), not at normal verbosity.
- [tested] Creating the simulation data before the hulls leaves the hulls on disk (24 of them) but behaves like no hulls: 0 break events and both no-geometry lines. Build in this order: fracture, hull step, `InvalidateCollection`, then `CreateSimulationData`.
- [tested] `UGeometryCollection::UpdateGeometryDependentProperties` as the hull step gave 25 hulls (the root too) and 24 breaks.
- [general] In a native project a collection built with the two calls and no hulls acted as one inert particle (observed once in a consuming project on an earlier engine build; not reproduced in this repo): the strain and crumble calls did nothing. `GetValidConvexHullData` on the rest collection before saving gave 31 hulls and a 374 KB asset.
- [general] A noise point spacing of 1 cm gave a 39 MB asset and 250 cm gave 320 KB, so check the saved asset size.
- [documented] `ApplyExternalStrain` and `CrumbleActiveClusters` are also silent with no physics proxy: each sits inside `if (PhysicsProxy)` (`GeometryCollectionEngine/GeometryCollectionComponent.cpp` lines 6826-6832, 6850-6856).
- [documented] In the editor, `UGeometryCollection::UpdateConvexGeometry` (called by `UpdateGeometryDependentProperties`) builds hulls (`GeometryCollectionObject.h` line 863; empty outside `WITH_EDITOR`, `.cpp` lines 450-461). The load path at `.cpp` lines 1276-1292 swaps Convex for Box on an old asset; it builds none.

## Spawn order

- [general] The sequence that worked: `SpawnActorDeferred` for `AGeometryCollectionActor`, `SetRestCollection` on its component, then `FinishSpawning`.
- [documented] `SetRestCollection(const UGeometryCollection*, bool bApplyAssetDefaults = true)` (`GeometryCollectionComponent.h` line 867) resets the dynamic collection and calls `RecreatePhysicsState` (`.cpp` lines 5148-5168), so the source does not say a later call fails. The component is the actor's root (`GeometryCollectionActor.cpp` lines 38-39) and registers in `PostSpawnInitialize` even when construction is deferred (`Engine/Actor.cpp` lines 4334-4337); `BeginPlay` runs from `FinishSpawning` in a started world (lines 4420, 4529), so the sequence sets the collection first.
- [tested] `SetRestCollection` after `FinishSpawning` also broke all 24 pieces, so one run did not show the deferred order to be required.
