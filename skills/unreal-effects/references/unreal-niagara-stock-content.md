# Niagara families and stock content

Public Epic pages below were read as UE 5.8 documentation on 2026-10-16/17. Only the "Stock content checks" subsection was run, by [`niagara_validate.mjs`](../../../examples/unreal/niagara_validate.mjs) on a throwaway project (the Custom material node and instancing facts stay in the production stack). Check the consuming project's installed APIs and settings. The materials, motion and cost review that goes with it is in the [Unreal production stack](../../unreal-rendering/references/unreal-production-stack.md).

## Author a compact Niagara family when it helps

- [documented] Tooling (Python versus C++ authoring, Epic's Niagara toolsets, MCP, sim-cache particle counts), see [Niagara in Unreal](unreal-niagara.md).

- [documented] Niagara supports mesh, sprite and ribbon renderers and particle-to-material bindings. Use authored silhouettes, flipbook breakup, age-driven erosion and distinct curves; verify facing, sockets, local/world space and actual event payloads. Component Renderer adds per-component overhead; avoid a SceneComponent for every decorative particle. [Epic: Niagara Renderers](https://dev.epicgames.com/documentation/en-us/unreal-engine/render-module-reference-for-niagara-effects-in-unreal-engine)
- [general] Keep existing valid signals and migrate one effect family first. A useful payload includes source/contact transform, velocity/normal, surface, strength, sustained state and event time as needed. Author player-critical accents and distant cosmetic tails separately so scaling can retain information. Niagara itself supplies neither the art direction nor the gameplay authority.
- [documented] Effect Types share scalability rules; System/Emitter overhead remains with GPU simulation. Set instance caps, significance/priority policy and bounds appropriate to the motion; verify player-critical cues survive culling and lower quality. Consolidate matching behavior when profiling supports it rather than moving every small effect to GPU simulation. [Epic: Niagara Scalability](https://dev.epicgames.com/documentation/en-us/unreal-engine/scalability-and-best-practices-for-niagara)
- [documented] Niagara's Baker can capture simulation as a flipbook. Try baked fluid motion for suitable smoke/fire before paying for live fluids; compare view-angle/depth limitations against a mesh core in the real camera. No bake or fluid performance is established here. [Epic: Flipbook Baker](https://dev.epicgames.com/documentation/en-us/unreal-engine/niagara-flipbook-baker-quick-start-guide-in-unreal-engine)

### Stock content checks

- [tested] Niagara is Unreal's own VFX system and is enabled by default; the NiagaraFluids plugin is not.
- [general] A native game links the `Niagara` module and spawns a system with `UNiagaraFunctionLibrary::SpawnSystemAtLocation`; observed once, not run here.
- [general] Editor Python exposes spawning and user-parameter setters on `NiagaraComponent`; observed once, not judged by the validator.
- [tested] Without the Experimental NiagaraToolsets plugin, Python cannot author the emitter stack: there is no Niagara editor library class, no `NiagaraMeshRendererProperties` class, and the system factory has no emitter-list attribute (setting one raises). With NiagaraToolsets enabled, authoring runs through `unreal.ToolsetRegistry.execute_tool`; routes and C++-only gaps: [Niagara in Unreal](unreal-niagara.md). Otherwise use Epic's systems or the Niagara editor.
- [tested] The default template systems are in `/Niagara/DefaultAssets/Templates/Systems/` (AttributeReaderTrails, DirectionalBurst, DirectionalBurstLightweight, FountainLightweight, MinimalLightweight, RadialBurst, SimpleExplosion), and the default template emitters are under `/Templates/Emitters/`. None of the systems is a fire.
- [tested] `FountainLightweight` lists no user parameters, so code cannot recolour or restyle it through the user parameter list. As a control, the fluids fire template lists `User.SimRT`.
- [general] `FountainLightweight` is a stateless (lightweight) particle fountain, and its additive white sprites vanish against a light background: put a dark backdrop behind effects. Observed once, not judged by the validator.
- [tested] The Niagara Fluids plugin (not enabled by default) ships fire templates such as `/NiagaraFluids/Templates/Gas/2D/Systems/Grid2D_Gas_MovingFire`. Its only user parameter is `User.SimRT`, a render target object. It has two emitters. `SourceParticles` holds one sprite renderer with material `M_Alpha`. `Grid2D_Gas_SmokeFire_Emitter` holds two renderers, with materials `M_2D_GasBase_Inst` and `M_Alpha`. No emitter names `M_2D_SmokeFire` directly. `GetEmitterTopology` refuses the grid emitter (`Script 'EmitterSpawnScript' not found in stack reference`), so read its renderers with `GetRendererData` by index.
- [tested] The material `M_2D_SmokeFire` exists, is translucent and unlit, and has the scalar parameters TemperatureCurve, DensityScale, TemperatureGain, DepthFade, Blackbody and TemperatureMaximum and the vector parameters `Density Tint`, `Temperature Tint`, EnvironmentColor and SunColor.
- [general] Each fluid instance runs its own grid simulation, so N fires cost N simulations; fire and smoke come from the same grid. Observed once, not judged by the validator. Whether a component-level material override removes the smoke was not tested.
- [general] Creating instances of the fluid system the first time logged a non-fatal engine ensure: "The current loader 'ZenLoader' is unable to FlushAsyncLoading from the current thread ... Flush will be ignored". The system still ran. Observed once, not judged by the validator.
- [general] To use engine-plugin Niagara content in a cooked game, enable the plugin in the `.uproject` and add `+DirectoriesToAlwaysCook=(Path="/Niagara/DefaultAssets/Templates/Systems")`, and the Fluids path for fluid systems, to `Config/DefaultGame.ini`. The comparison-scene flow exercises it; the validator does not judge it. Side-by-side harness: [comparison scene](../../unreal-native/references/unreal-native-compare-scene.md).
