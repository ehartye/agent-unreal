# Niagara ink looks: outlines, ribbons, mesh particles and cost

Written for Unreal 5.8. [`stylized_validate.mjs`](../../../examples/unreal/stylized/stylized_validate.mjs) runs each [tested] line and its [README](../../../examples/unreal/stylized/README.md) lists the stations. The drawn flipbook and the stepped light are in [Niagara: drawn, ink and cel looks](unreal-niagara.md); this page adds an outline, ribbons, mesh particles and cost.

Every [tested] line is a record of three runs on 2026-10-30, each covering all four groups: one machine, offscreen Play-In-Editor, a viewport of 1014 by 550, small scenes. A method counted as working when a pixel check on the captured frame found a ring of the outline colour around the shape, never by eye. A result that did not hold is kept as a negative. Nothing here says why a method worked or failed unless a run showed it; the rest is marked not established.

## An outline on a particle

- [documented] No source in the wiki shows an outline on a Niagara translucent particle. McGuire and Fein (NPAR 2006) outline a particle cloud with a slightly larger copy of the coverage mask, a small depth offset behind the billboard, so the ordinary depth test hides interior outlines (wiki: Cel-Shaded Particle Rendering). Tom Looman's tutorial outlines meshes marked for custom depth with a post process that reads custom stencil, and says nothing about particles (same page).
- [tested] Stencil outline, runs 1 to 3: on the drawn flipbook sprite it drew a ring (5,492 outline pixels, ring coverage 1.0, every pixel different from the frame with the post process off) and on a mesh particle (5,104 pixels, coverage 1.0); the same in all three runs. The setup the runs used: `r.CustomDepth=3` in the project, `render_custom_depth` on and `custom_depth_stencil_value` 1 on the Niagara component, and an unbound Post Process Volume with a material at Before Bloom that colours a pixel where the stencil is 0 and a pixel within 6 or 3 pixels of it is above 0. Whether each part is required was not tested one at a time.
- [tested] Coverage ramp, run 3: the sprite's own material dilated the flipbook alpha by the largest of 16 texture taps (radius 0.04 and 0.02 of the sprite) and coloured the difference. It drew a ring (16,734 pixels, boundary coverage 1.0, hugging 1.0; the no-outline control frame had 0 pixels). The taps were plain texture samples at one fixed cell of the atlas, on a renderer left at the default 1 by 1 sub-image size. Run 1: with a SubUV sample node and an offset on its UVs input there was no ring. Run 2: with the renderer at 4 by 4 the frame showed the whole quad as a magnified patch of the cell. The cause of each was read from the frame and is not established.
- [tested] Coverage flange, run 3 (negative): a second sprite renderer on the same particles drew the dilated coverage in the outline colour, pushed 25 units away from the camera with a world position offset. It drew a copy of the dilated shape, enlarged and displaced mostly to the left of the body (the log says down and to the left), partly outside it and partly behind it (ring coverage 0.70, 19,367 pixels, hugging 0.91); not a ring. In run 1 the material did not compile: `External code identifier 'CameraVector' is not available in the EMaterialShaderFrequency::Vertex shader`, and the default material drew. Run 2 drew the whole quad in the outline colour behind the body, probably the ramp's UV fault (an inference from the frame, not shown). Why run 3 displaced the copy is not established. Smallest next experiment: replace the offset with a `Transform` node taking (0, 0, 25) from camera space to world space and check the frame for a ring. Overlap of several particles was not tested.
- [tested] Setup discovery on the editor Python API, before the counted runs: `unreal.MaterialProperty` has no pixel depth offset member, so a depth push in a particle material is a world position offset.
- [general] Pick the stencil outline when the shape is a whole renderer (sprite, ribbon or mesh): it needed no change to the particle material. Pick the coverage ramp when only the sprite's own material may change and the shape is a flipbook's alpha. Do not use the flange as built.
- [general] Not established by any run: a stencil outline around a cloud of overlapping particles, whether the outline survives sorting against other translucent effects, the stencil outline on a Substrate Toon material, and its cost.

## Ribbons and mesh particles

- [documented] No wiki source covers an ink look on a ribbon or a mesh-particle renderer. The usage flags for sprites, ribbons and mesh particles are separate material properties ([Toolset renderers](unreal-niagara-toolset-renderers.md)).
- [tested] Ribbon, runs 1 to 3: the unlit stepped-light material (a cylinder normal across the width, quantized with `floor` to 4 levels) drew 4 flat bands (flat share 0.96, 5 levels) beside a smooth control with 13 levels. The ribbon was a StaticBeam in local space, 2,400 units long, Beam Width 250, 100 particles, UV0 V across the width.
- [tested] Ribbon outline, runs 1 to 3: an edge ramp in the material (coverage across the width above 0.8) drew a ring on both long edges (58,880 pixels, coverage 1.0; 23 pixels each side in run 1) and the stencil outline drew a ring (15,360 pixels, every pixel different from the stencil-off frame).
- [tested] Mesh particle, runs 1 to 3: the engine sphere (scale 3) on a one-particle sprite emitter with the sprite renderer disabled and an override material (`OverrideMaterials`, `explicitMat`) lit from the world normal drew 4 flat bands (flat share 0.965 to 0.967) beside a smooth control with 17 levels; the stencil outline drew a ring (5,104 pixels). The coverage ramp is a sprite-material method and was not run on a mesh.
- [general] Set the material per renderer and read the frame; a ribbon or mesh that shows the default material has a missing usage flag until proven otherwise.
- [general] Not established by any run: a mesh renderer with many particles, a ribbon that curves or twists, ribbons of different widths, and a lit material on either renderer.

## What the look costs

- [documented] The wiki sources give no frame cost for any ink look (Making Ink-Like and Cel-Shaded Niagara Effects). The Overwatch poster counts texture memory, authoring time and repetition for a drawn flipbook, not frame time (same page).
- [tested] Run 3 (run 2 agreed): 2,048 translucent sprites of 800 units stacked in one spot, 290 frames per window after trimming, two interleaved rounds per scene agreeing within 0.2 percent, median `GPUTime`: plain unlit control 3.335 ms, ink look (steps and a ring from the radial coverage) 3.339 ms, so +0.004 ms (run 2: -0.002 ms). The drawn look with the 16-tap outline read 6.448 ms, +3.11 ms over the control. The gate required other GPU users under 10 percent before and after; they read 1 to 2 percent.
- [tested] Run 1: 256 stacked sprites read 1.33 ms in all three scenes, no measurable difference. Runs 2 and 3 read 3.3 ms with 2,048 sprites (800 units here, 1,100 in run 1), so the particle count or size raised the time and the ink maths did not; the log put it at about 1.15 microseconds per added stacked layer.
- [tested] Run 1: frame time read 8.33 ms in every scene (the 120 fps cap), so only the GPU time figure separates scenes.
- [general] These scenes are blend-bound by construction. They say the ink maths added no measurable time when blending dominated, and that 16 extra texture reads per pixel added about 3 ms at 2,048 overlapping layers. Budget a sparse effect by measuring it.
- [general] Not established by any run: the cost of the stencil outline (the cost scenes held no stencil pass), of a ribbon or a mesh particle, of the look on a sparse effect or at another resolution, and any result on a second machine. A run 1 reading was lost to a profiler-file reader fault, not an engine result: the CSV profiler file has its header first and last and rows of differing length.

## Friction found

- [tested] Run 1: `CameraVectorWS` is rejected in a vertex-shader input, so a world position offset cannot read the camera vector.
- [tested] Run 1: a SubUV sample node with an offset on its UVs input did not produce the offset result. The ramp that drew a ring used plain texture samples at a fixed cell.
