# Simulated key and click on a Common button: partial

Target: Unreal Engine 5.8 on Windows. Everything marked tested was run on 2026-10-30 as A-Q4 run 1 to 3 ([the probe](../../../examples/unreal/umg/README.md), group `input`), in the Common UI project of [Common UI setup](unreal-umg-common-ui.md), in an offscreen Play In Editor session with an activatable widget active, Epic's MCP server and the Slate inspector toolset. Verdict: partial. The Slate inspector reached editor widgets and saw the Common button; no route changed the button.

- [tested] A-Q4 runs 2 and 3: no route changed the Common button. The observable was wired: the stage script bound the button's `on_button_base_clicked` delegate (one argument) to a handler that logs `CLICKED count=N`, and calling `OnButtonBaseClicked.broadcast(button)` from the script logged `CLICKED count=1` (the control). `on_clicked` is not exposed to Python as a delegate on the Common button.
- [tested] A-Q4 runs 2 and 3, the routes tried: `set_focus()` (run 3) and, in run 2, `set_user_focus(controller)`, `set_keyboard_focus()` and `WidgetLibrary.set_focus_to_game_viewport()` each returned None and `has_any_user_focus` stayed false; the player controller has no `input_key` in Python; the button has none of `simulate_click`, `simulate_button_click`, `click`, `press`, `simulate_press`, `trigger_click`; the activatable widget's `on_key_down(Enter)` returned an `EventReply` and the counter did not move. The Slate inspector (described in [the overview](unreal-umg-overview.md)): `Observe` then `Snapshot` listed the active button (`generic "GO"`, with a `ref`), and `Hover`, `Click` and `PressKey Enter` on it each returned true, the counter stayed 0 and `is_hovered`, `is_pressed`, `has_any_user_focus` and `has_keyboard_focus` stayed false. In run 2, clicks after a hover and after setting an input mode and showing the cursor did the same.
- [tested] A-Q4 run 3: the Slate inspector's `Click` on the editor's Content Drawer button returned true and the snapshot grew from 347 to 425 lines (the drawer opened, visible in the frame). So the inspector's calls reach editor widgets in the offscreen editor. A frame difference alone is not evidence: the frames differed by 248,649 pixels with the drawer open in the frame before and closed in the frame after, while the GO button and the title text were identical in both.
- [tested] A-Q4 run 3, seen once and not settled: the snapshot reports the button as 598 by 173, about twice the size it has in the frame (about 304 by 88), the inverse of the viewport's UI scale; if the tool clicks the middle of the reported size, that falls inside the button by about 5 pixels at its right edge and 1 to 2 at its bottom edge. A miss by aim is not ruled out, and neither is an event dropped for lack of Slate focus; the runs cannot tell them apart.
- [tested] A-Q4 runs 2 and 3: Python has no `input_key` on the controller. Enhanced Input `InjectInputForAction` (needs an input action asset bound to the button), `FSlateApplication::ProcessKeyDownEvent` (C++) and the Automation Driver (the inspector's own description says it deadlocks on the game thread) were not tried.
- [general] Next experiment: repeat the inspector `Click` with a viewport whose UI scale is 1, or a button large enough that the middle of the reported size is well inside it, and read the same counter. If that fails, find why `has_any_user_focus` stays false in the offscreen editor.

## Not established

- [tested] A-Q4 runs 1 to 3: that any simulated key or click changes a Common button, and which widget receives it. Gamepad events and a physical device need a person.
